# mk300 — design

Date: 2026-09-16. Status: approved in chat, pending spec review.

## Goal

A sibling of [hotone-ampero-2](https://github.com/jpfaria/hotone-ampero-2) for the
**M-VAVE MK-300**: the reverse-engineered USB-MIDI protocol, a Python library + CLI
(`mk300`), and a Claude Code plugin with two skills (`mk300`, `tone-builder`). Feature
parity with `ampero2` wherever the MK-300 has the feature; what the pedal lacks is
documented as absent, never emulated.

## Ground truth (checked 2026-09-16)

- Pedal on USB, CoreMIDI port `USB Composite Device` (name to be confirmed from the
  first capture; the library keeps it a constant like `ampero2.device.PORT_NAME`).
- Editor `/Applications/M-EFCS.app` (`com.digAmp.dgAmp` 3.7.1413), Flutter, MIDI through
  `flutter_midi_command` (so: SysEx over CoreMIDI, same transport as the Ampero), BLE
  through `flutter_blue_plus` (ignored: USB only). Native libs: `libamx_parser.dylib`
  (AMP/DS model files?), `libsinco_audio.dylib`, `libstemsep_api.dylib`, onnxruntime.
- Editor assets `flutter_assets/lib/resources/bin/mk300/`: `mk300_am3_preset.bin`,
  `mk300_am4_preset.bin`, `mk300_am3_ampCab.bin`, `mk300_am4_ampCab.bin`, `mk300_drum.bin`,
  `mk300_midiDrum.bin`. Model/parameter tables are expected there and/or in strings of
  `App.framework` (Dart AOT).
- MIDI Monitor installed.

## Method

The Ampero method, unchanged: MIDI Monitor spies the editor's port; Claude drives M-EFCS
(computer-use, one action per capture) and the user steps on the pedal when a footswitch
action is needed; each capture is saved as `.mmon` (Copy truncates long SysEx) under
`docs/captures/` and decoded by `mk300.mmon_export`. Every message the library sends is
one the editor was seen sending. Findings go to `docs/protocol.md` as they are proven;
golden vectors go to `tests/fixtures/`.

Static analysis (strings / the `.bin` tables) only feeds the catalog; it never decides
what to send to the pedal.

## Structure (mirror of ampero2)

```
mk300/            protocol.py (frame, checksum, encode/decode), device.py (transport),
                  patch.py (dump image), catalog.py + catalog.json + catalog_build.py,
                  resolve.py, ir.py / amp.py (uploads), reamp.py, mmon_export.py, cli.py
docs/protocol.md  the protocol, docs/captures/ the raw evidence
tests/            golden vectors from the captures; tests/tone_builder/
skills/mk300/     SKILL.md + reference.md (generated by tools/build_reference.py)
skills/tone-builder/  SKILL.md + reference.md + scripts/build_patch.py, analyzer.py
.claude-plugin/   plugin.json + marketplace.json (marketplace `mvave-mk-300`, plugin `mk300`)
pyproject.toml    package `mk300`, console script `mk300`, Python >= 3.11,
                  deps mido, python-rtmidi, tone-analyzer; extra `reamp`
```

## Functional scope (parity list, each item = a capture + a message in protocol.md)

1. Patches: list names, load, read (dump), save, copy.
2. Edit buffer: knob value per slot/param, block on/off, model per slot (from catalog).
3. Patch-level: name, tempo, volume, footswitch/expression assignments, whatever else the
   MK-300 exposes per patch.
4. Global settings: read pages; write **one field at a time** with read-back, only ids seen
   from the editor.
5. Inventories: patches, user IRs, user AMP/DS models, firmware.
6. Uploads: IR (`.wav`), AMP and DS third-party files (whatever the editor converts through
   `libamx_parser.dylib` is called through ctypes, like `HTUSBTools`), delete/rename.
7. `reamp DI.wav OUT.wav`: the MK-300 is a 24-bit/44.1 kHz USB audio interface; routing
   confirmed by a spike (same as the Ampero spec: find the patch input-source byte or use a
   prepared REAMP patch).
8. `listen`: whatever the pedal broadcasts on footswitch changes.
9. `resolve`, `models`, `params`: catalog queries by real-world gear name.
10. Skills: `mk300` (talk to the pedal, hard rules) and `tone-builder` (port of the Ampero
    one; same two-layer rule: the tone layer shells out to `mk300` and `tone-analyzer`).

Unknown until captured (documented as such, not assumed): scenes/snapshots, number of
slots and patches, compression/encoding of dumps, whether models are addressed by code or
index. The MK-300 has no editor-visible "scene" feature in its manual; if there is none,
the CLI has no `scene` command and the tone-builder builds single-state patches.

## Safety rules (carried over)

- Only send frames observed from the editor. No id/value probing.
- Global writes one at a time, read back, stop on timeout and tell the user.
- A SysEx hang = power cycle + a line in `docs/protocol.md` Pitfalls.
- Uploads verified byte-for-byte against the editor's own image before being sent.

## Testing

Pure functions (frame encode/decode, checksum, image parsing, catalog, resolve) get unit
tests on golden vectors from captures. Transport is a thin class exercised only against the
real pedal, by hand, at each phase's end. tone-builder tests reuse the Ampero fixtures
pattern (fake `mk300`/`tone-analyzer` CLIs).

## Order

1. Captures + `docs/protocol.md` (connection, patch list, load, read, param, on/off, model,
   save, globals, inventories, uploads).
2. `mk300` package: protocol, device, patch + tests.
3. Catalog from the editor tables + `resolve`.
4. CLI with the same verbs as `ampero2` (minus what the pedal lacks).
5. Uploads + reamp (spikes first).
6. Skills, plugin manifests, README, `tools/build_reference.py`.
